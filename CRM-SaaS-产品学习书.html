Part 1 · 核心业务

第 1 章 · CRM 的核心业务

01

先回答最根本的问题：CRM 这门生意，到底在经营什么？两家公司如何把它包装成产品矩阵并卖出去？

学习目标
  • 能用一句话说清 CRM 的业务本质，并画出"营销-销售-服务-渠道"四域全景；
  • 能对比两家产品的定位、客群与行业打法；
  • 能拆解 CRM SaaS 的商业化公式：订阅 × 版本分层 × 版块加购 × 实施费。

1.1CRM 到底经营什么

B2B 交易的特点是链条长、角色多、周期久：一条广告线索要经过市场、销售、商务、财务、售后多个角色，几个月到一年才变成回款。CRM 的业务本质，就是把这条链路上的三样东西数字化并管理起来：

① 客户资产（Account 360）
客户与联系人不再是销售个人手里的 Excel，而是企业的数据资产：查重、查工商、客户树、权力地图（决策链），人走了，资产留下。
② 销售过程（Pipeline）
把"感觉能成"变成可管理的阶段：分阶段推进、每阶段有进入/完成条件、漏斗与赢率可度量、预测有依据。
③ 回款兑现（Cash）
中国版 CRM 特有的重心：合同、订单、、开票、收入确认——"签了合同不算成，钱到账才算成"。
外延：把链路两端也连起来
往前连营销（获客），往后连服务（复购），往外连渠道伙伴（分销）——这就是"营销服一体化 + 渠道"的产品矩阵由来。

  • 行业方案：14 个行业 + 6 个场景方案（国产替代 / 企业出海 / Salesforce 迁移 / 大客户 KA / 交付项目管理 / 售后服务），覆盖 54 个细分类目✅

Part 2 · 系统架构

第 2 章 · 系统的架构

02

剥开业务功能看骨架：两家产品在架构上高度同构——多租户 SaaS 基座 + 元数据驱动 PaaS + 按云组合的业务应用 + 多端 + 开放生态，差异只在个别层的取舍。

学习目标
  • 能画出 CRM SaaS 的六层架构，并说出每层职责；
  • 理解"元数据驱动"为什么是 SaaS 可配置性的根基；
  • 掌握四类权限设计，以及 AI 原生时代架构新增的语义层。

2.1六层总体架构

读架构的方法：判断一个 CRM SaaS 的成熟度，先看三层——基座（是否真多租户、容灾合规）、平台层（配置颗粒度：能否自定义对象/流程/权限）、连接层（API 是否对象级标准动作、有没有 iPaaS）。业务功能反而最容易模仿。

2.2元数据驱动：SaaS 可配置性的根基

为什么一个 SaaS 产品能同时服务几千家有不同流程的企业？答案是元数据驱动架构：客户的"自定义"不是改代码，而是往元数据里写配置——对象、字段、布局、流程、规则都以元数据形式存储，运行时统一解释执行。

元数据与开发范式两家都在对标 Salesforce 的开发体系
纷享销客
  • 可视化对象设计器：无代码创建业务对象、扩展字段、配置界面✅
  • 沙盒（镜像环境）+ 更改集 + 软件包：一键部署到正式企业；软件包可跨租户复制，沉淀行业/ISV 方案✅——直接对标 Salesforce 的 Sandbox + Change Set
  • 高代码：APL（Java/Groovy 服务端）+ PWC（前端组件/插件），WebIDE / VSCode 工具链✅
销售易
  • 可视化业务建模：拖拽完成对象/字段/关系建模，"数据模型自管理"✅
  • 四类 API：Open API / Bulk API / （自研查询语言）/ Meta API（直接暴露元数据）✅
  • 高代码：触发器 Trigger + Java/H5 全代码套件 + SDK；沙盒环境 + 制品跨环境迁移✅
  • 前端组件级开放：官方 neo-cmp-cli 支持 React/Vue 自定义组件发布上平台✅
学习要点：判断一个平台是否"真 PaaS"，看三个证据——①能否自定义对象（而不只是自定义字段）；②开发有没有沙盒与制品迁移；③元数据本身有没有 API（销售易的 Meta API、纷享的软件包机制）。营销话术会混淆"低代码表单"与"元数据平台"，用这三条去验证。

2.3组织与权限架构：RBAC + ABAC

CRM 权限设计要同时回答"谁能用什么功能"和"谁能看哪些数据"。 管角色授权， 管按属性动态过滤数据——销售易官方明示双模型并用；纷享以"多维多级权限"表述并额外设计了外部权限体系支撑跨企业场景。

2.4AI 原生架构：2025-2026 的新平台层

两家在 2025 年同步发布 Agent 版产品、2026 年同步升级"AI 原生"，而且都把 AI 做成平台层而非插件——但技术路线不同：

AI 平台路线自研 AgentOS 多模型开放 vs 业务语义层绑定混元
纷享 · ShareHive 蜂巢 AgentOS
  • 三层结构：五层语义建模 + 三层 Know-How 系统 + Agent 应用市场，统一数据底座✅
  • 组件：Agent Studio（构建器）、ShareAgent、提示词模板、语义检索索引、对象 AI 组件、计费与用量管理✅
  • Agent 按业务域开箱分发：营销 / 销售（线索、客户、商机、报价订单、销售行为五组）/ 服务 / 分析 / 知识库✅
  • 多模型开放接入（千问、豆包等办公连接器）✅
销售易 · 业务语义层 + NeoAgent 2.0
  • 底座：业务语义层（AI 理解业务语义后自主推理决策）+ 可信数据层（Data Cloud 支撑推理负载）✅
  • 五类角色 Agent：营销 / 销售 / 服务客服 / 渠道经理 / 分析师；销售 Agent 可解释商机健康度评分、行动建议一键转任务✅
  • Agent 开发平台：Prompt Builder / Agent Builder / Agentic RAG / 可视化调试⚠️ 详情官网未展开
  • 模型绑定腾讯混元 + DeepSeek✅
学习要点：AI 进 CRM 后，配置对象从 CRUD 扩展到 Prompt / Agent / RAG / 用量计费。两家共同做法值得记住：预置角色化 Agent（开箱）+ Agent 开发平台（自建）两层，和"标准功能 + PaaS 定制"是同一个设计模式在 AI 时代的重演。

3.1L2C 主流程：从线索到订单的六个阶段

纷享官方称其为 （Lead to Order，销售线索到销售订单的端到端流程），共六个阶段；销售易的 L2C（Lead to Cash）把回款也纳入主流程。两个名字，同一条链。

逐阶段拆解：对象 · 角色 · 规则

  1. 市场获客　对象：市场活动、活动成员、销售线索。动作：创建活动、维护成员、关联线索、ROI 归因。纷享在此阶段即引入"标讯通"等潜客入口；销售易对应市场活动（SFA-01）与广告数据回流。✅
  2. 线索接入、分配与验证　对象：。规则三件套：查重（避免撞单）、评分（行为积分/智能打分）、线索池（分配-回收-保有量）。线索状态机：未分配→待处理→跟进中→已转换/无效/已作废。✅
  3. 客户与联系人　先查重再建档；客户资源经流转（领取/分配/退回/规则回收），公海规则提升资源利用率——官方特别注明"公海不等同于客户生命周期本身"。✅
  4. 商机推进　对象：商机、商机明细、商机联系人、。销售流程 = 进行中阶段 + 终结阶段，每阶段可配停留时长、提醒、审批、进入/完成条件、是否允许跳过，支持多套流程并存（如按行业/产品线）；输出赢单/输单/无效。销售易对应销售阶段（SFA-12）、关键事件（SFA-13）、作战地图（SFA-16）。✅
  5. 产品配置、定价与报价（CPQ）　链路：产品与分类→属性与→可售范围→价目表→报价单→订单。注意：价格政策（折扣/减价/买赠）与价目表是两个概念——价目表定基准价，价格政策定让利规则。✅
  6. 确认交易　对象：销售订单、订单产品、销售合同。四种成交模式：报价转订单 / 框架合同分批执行（合同→多订单）/ 订单关联合同 / 直接下单。✅
三类运行基础能力（纷享官方从 LTO 总览中提炼，值得背下来）：客户数据基础（查重、归属、公海、保有量、权力地图）；交易基础（产品与单位、价目表、可售范围、价格政策、信用规则）；过程分析（营销归因、阶段转化、滞留、流失、输赢单分析）。

3.2订单后延伸：从 Order 到 Cash 的中国化改造

Salesforce 经典模型到 Order 基本收尾；中国 CRM 因为赊销普遍 + 经销商体系复杂，必须把财务语义接进来。纷享的"收入管理"给出了教科书级的三类立应收场景：

周期性立应收
订阅/循环计费场景：按周期自动生成本期应收，SaaS、租赁、维保类业务的核心。
合约立应收
基于合同或订单的付款计划生成应收，配合回款计划跟踪与预警。
结算立应收
基于实际交付结果（对账单/结算单）生成应收，工程、贸易类业务常用。
销售易的对应设计
回款计划 → 回款记录核销 → 开票申请 → 收入确认计划（华为云手册第五章专门章节），另设合同变更单管控。✅

第 5 章 · 生态的打造方式

05

单点产品做不到规模化覆盖中大型企业的全部系统，生态是 SaaS 的第二增长曲线。中国 CRM 的生态打法与 Salesforce 的 AppExchange 模式很不一样——先看全景，再逐层拆。

5.1生态全景：四层连接

5.2开放平台：API 设计哲学对比

OpenAPI 与 iPaaS"每个对象一套标准动作" vs "四类 API 分层"
纷享销客
  • OpenAPI 覆盖 CRM 全部对象，每个对象提供 get / list / queryCount / create / update / delete / invalid / operate / attachment 等标准动作✅
  • 鉴权：应用级 corpAccessToken + 用户级授权双轨；应用免登/纷享免登；全局返回码体系
  • 数据集成平台（iPaaS）：预设连接器，对象/字段映射、单向/双向同步；ERP 插件（SAP/金蝶 K3 Cloud/用友 U8 Cloud）；单租户独立 PostgreSQL 库支撑同步隔离✅
  • 移动端 JS API：扫一扫/选人/分享/收藏
销售易
  • 四类 API：Open API（业务）/ Bulk API（批量）/ XOQL（自研查询语言）/ 自定义 API；Meta API 暴露元数据✅
  • OAuth2 授权码/密码模式（密码拼接 8 位安全令牌）；在 CRM 管理端"连接器"自助创建 Client_ID/Secret✅

学习要点：纷享走"对象级标准动作"路线——学一次动作集就懂全对象 API，对集成商友好；销售易走"API 分类分层"路线——批量、查询语言、元数据各就各位，更接近 Salesforce 的 API 矩阵。两家都有 iPaaS 低代码连接器，说明纯 API 时代正在让位于"配置化集成"时代。

5.3超级 App 路线：全押 vs 单押

中国企业的工作入口在超级 App（钉钉/企微/飞书）手里，CRM 必须决定"住在谁家"：

纷享：三线全押，做跨生态标准件
  • 钉钉版 / 企微版 / 飞书版 CRM 都是成熟产品线；公众号/小程序集成引流
  • 不站队任何协同平台 → 可触达三平台企业客户池，代价是没有独家流量倾注
  • 2026 年新增 workbuddy / 千问办公 / 豆包工作连接器——AI 办公入口同样全押✅
销售易：单押腾讯，换排他性资源
  • 企微做连接与私域（SCRM/上下游）、腾讯云做基座与出海、混元/DeepSeek 做模型
  • NeoAgent 与腾讯桌面智能体 WorkBuddy 通过 Connector 深度集成；发布节奏绑定腾讯云城市峰会✅
  • 获得腾讯云/企微排他性背书，代价是生态半径受腾讯体系约束

5.4上下游网络：本世纪中国 CRM 最有意思的架构发明

品牌商想连接经销商、厂商想连接服务商——但这带来一个架构难题：伙伴公司不是你的员工，不该进你的租户；可协作又必须跨企业读写数据。两家给出了教科书级的两种答案：

跨租户互联 vs 单租户 PRM网络效应与部署轻重的取舍
纷享 · 企业互联 CPaaS + 集团 1+N
  • 伙伴是独立租户，通过互联平台连接：互联企信（跨企业 IM）、互联通讯录、互联角色/部门、互联账号自注册✅
  • 互联应用：数据同步、订货通、报数通、伙伴学堂、互联网盘、互联服务号、跨企业审批✅
  • 集团 1+N：统一主数据管控 + 跨租户业务协同 + 分级分权✅
  • 网络效应：下游伙伴被"链"上来后也可能整体采购纷享 → 链式获客
销售易 · 伙伴云（单租户 PRM）
  • 伙伴门户是厂商租户内的模块（Salesforce PRM 思路）：招募/登记审批、政策公告、绩效目标、数据分析✅
  • 对人的触达借助企微上下游：上下游群聊、数字渠道空间小程序——伙伴不需要买销售易✅
  • 三层架构：PaaS 底座 → 厂商管理引擎 → 经销商 PRM 门户❓第三方分析
  • 部署轻、上线快；网络效应弱于跨租户模式
学习要点：这组对比是全书含金量最高的架构决策案例——把"连接"做进架构（跨租户网络）还是做进功能（租户内模块+外部 IM）。前者换长期网络效应与续费粘性，后者换交付速度与低成本。没有标准答案，取决于行业链主的话语权强度。

  • 记住通用搭建公式，并能说出中国市场的四大本土化增量。

6.1标准化光谱：个性化的四级收敛

核心洞察：SaaS 公司的竞争力 = 把客户需求从第④层"搬"到第②层的能力。每搬一层，交付成本降一级、复制速度升一级。两家帮助中心里那些厚厚的"管理员配置指南"，就是这场搬运的战场。

6.2九项具体设计拆解

以下每项都按"设计思路 → 两家印证 → 学习要点"展开。这是本章的正文主体，建议逐条对照第 2-5 章的实例回看。

① 对象与字段可配置——元数据是唯一的真相源

设计思路：标准对象覆盖 80% 场景，自定义对象承接行业差异；字段、布局、校验规则全部元数据化，运行时解释执行。

纷享：可视化对象设计器 + 界面定制（"千企千面"按角色出布局）+ 通用业务规则配置；对象定制已内置 AI 能力子项。
销售易：可视化业务建模 + Admin 系列（校验规则/查重规则/关联关系/引用字段/主子明细）+ Meta API 暴露元数据本体。

学习要点：判断配置颗粒度看三问——能否新建对象？字段级能否控权限？元数据能否被 API 读写？

② 流程引擎——把组织里的"走流程"抽象成三种引擎

设计思路：审批流（人事审批）+ 业务流（单据流转，如商机阶段）+ 工作流/自动化（数据驱动的后台规则）三类引擎分离，覆盖企业 90% 流程需求。

纷享：审批流、业务流、工作流、阶段推进器并列；流程后动作（无代码）+ 插件自定义函数；流程运维与效能分析（审批超时监控）。
销售易：可视化流、工作流、自动流三类 + 事件驱动规则引擎 + 触发器 Trigger（代码级）；工作流支持对象全生命周期。

学习要点：流程引擎的成熟标志不是"能配多复杂"，而是流程运维——超时监控、批量转交、版本升级时在途单据怎么办。

③ 资源流转规则——公海是"销售管理制度"的产品化

设计思路：把销售管理的制度诉求（客户不捂死、撞单有裁决、资源可再分配）转译成五要素规则：准入、查重、保有量、回收、保护期。

纷享：客户查重规则、归属规则、创建识别与审批、保有量上限；线索侧同构（线索池/分配/回收）；官方文档明确"公海 ≠ 客户生命周期"。
销售易：线索/客户双公海池、分组成员可见性、循环回收；团队成员继承规则解决"流转后协作权限"的边缘情况。

学习要点：这类"规则引擎型功能"最能体现 SaaS 标准化功力——同一套引擎，快消行业配出强回收，大客户行业配出长保护期。

④ 权限模型——RBAC 管功能，ABAC 管数据，外部权限管企业边界

设计思路：见第 2.3 节四象限。标准化关键在于：权限继承 PaaS 角色体系（BI 字段级权限继承即是例证），且权限可诊断（纷享有"权限诊断与排查工具"）。

纷享：功能权限到字段级/界面级；数据权限支持多区域、多产品线；独有外部权限体系支撑互联场景。
销售易：官方明示 RBAC+ABAC 双模型；用户-角色-职能-数据四层 Admin 文档；团队成员继承。

学习要点：权限设计的难点排序：数据权限（多维交叉）＞ 外部权限（跨企业）＞ 功能权限（成熟方案已收敛）。

⑤ 版本分层与功能门控——用价格表表达产品战略

设计思路：版本不是功能堆砌，而是"企业成熟度"的镜像：小微版给标准流程，旗舰版解锁定制化销售流程/多语言/高级 PaaS；付费版块（订货通/服务通…）按业务域加购。

纷享：公开价目（小微免费→企业版→营销版 + 专业/旗舰），实施费透明标价；付费应用清单逐项售卖⚠️清单待核。
销售易：专业→企业→旗舰→无限四档（官方不公示价❓）+ 云组合报价；以"易启"独立产品线承接小微，与主产品重配置形成两端。

学习要点：观察一家 SaaS 的版本表，就是在读它的目标客群战略——门控放在"流程引擎"还是"分析能力"上，暴露它认为谁愿意付溢价。

⑥ 行业模板——把项目经验变成可复制资产

设计思路：行业化三板斧：行业方案页（营销载体）→ 行业版/行业套件（产品载体）→ 行业 Know-How 进平台语义层（AI 载体）。

纷享：快消行业专设帮助频道（拜访管理/车销引单/TPM）；行业套件 + PaaS 软件包跨租户复制；ShareHive 宣称 15 行业 Know-How✅。
销售易：文档站单列"行业版产品"手册线；装备制造方案 = 集团架构管理 + 交付项目管理 + 选装选配 CPQ 三件套；BI 分行业分析模板✅。

学习要点：行业模板的终局是"新客户 = 选模板 + 改配置"，这正是第④层（定制实施）占比下降的过程。

⑦ 多端策略——一套元数据，多个壳

设计思路：自有端（Web/App）保完整体验，超级 App 版（企微/钉钉/飞书）保触达，小程序/H5 保轻量场景。关键是多端共用同一套对象与权限元数据，而非各自开发。

纷享：iOS/Android/Windows/Mac 全客户端 + 三大超级 App 版 + 移动端 JS API 开放；多语言（旗舰版）。
销售易：产品级对接企微/钉钉/飞书/腾讯会议；服务小程序；NeoUI 统一前端框架支撑自定义组件跨端。

学习要点：判断多端是真一体化还是"套壳"，看离线与冲突：移动端改的数据回到 Web 端是否一致、字段级权限是否跨端生效。

⑧ 集成标准化——从"写接口"到"配连接器"

设计思路：对象级标准动作 API（学一次懂全部）+ iPaaS 连接器（免代码集成）+ 事件订阅（准实时）+ SSO（身份打通），四级递进。

纷享：全对象 get/list/create/update… 标准动作 + 数据集成平台（ERP 插件、双向同步、单租户独立库）+ OA 待办打通。
销售易：Open/Bulk/XOQL/Meta 四类 API + 管理端自助连接器 + HiFlow 等第三方平台连接器 + SSO（预置上百应用认证组件）。

学习要点：集成能力是中大型客户续费的隐形护栏——ERP 同步一旦跑通，替换成本极高。这也是"连接型"叙事的商业本质。

⑨ AI 标准化——"预置 Agent + Agent 开发平台"双层结构

设计思路：把 AI 当平台层而非功能点：底层是语义层/Know-How（行业与业务词汇的机器可理解版），上层按角色预置 Agent（开箱）+ 提供构建器（自建），并引入用量计费。

纷享：ShareHive AgentOS（语义建模 + Know-How + Agent 市场 + 计费与用量管理）；Agents 按营销/销售/服务/分析/知识五域分发。
销售易：业务语义层 + Data Cloud 可信数据层；五类角色 Agent；Prompt/Agent Builder + Agentic RAG 开发平台。

学习要点：注意与第⑤⑥条的同构性——AI 的"预置 + 自建"正是"标准功能 + PaaS"模式的重演；语义层就是 AI 时代的"行业模板"。
